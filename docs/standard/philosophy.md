# Neptune. Signal Philosophy

Neptune. Signal is not a visual skin. It is the operating discipline for Neptune. financial products.

The design language exists to make money movement, identity, approvals, support, and account operations feel clear, fast, trustworthy, and unmistakably Neptune.

## The Core Idea

Signal means the customer always understands what matters now.

Every screen must answer:

- What is my current financial state?
- What changed?
- What can I do next?
- Is anything waiting for me?
- Is there risk, delay, or confirmation?

If a screen does not create a useful signal, it should be simplified.

## Neptune. Is the Structure

White-label banks may change color and branding, but they should still feel like Neptune. software underneath.

Neptune. stays present through:

- Information hierarchy.
- Motion behavior.
- Banking density.
- Account and transaction patterns.
- Consent and approval patterns.
- Performance decisions.
- Accessibility and language behavior.

## Banking Is Dense, Not Decorative

Customers open banking apps to understand and act. The interface should be rich but not noisy.

Use:

- Clear rows.
- Stable app shell.
- Compact account surfaces.
- Precise action groups.
- Status pages that show all required receipt information.

Avoid:

- Empty decoration.
- Repeated nested cards.
- Oversized marketing language inside app tasks.
- Random accent colors.
- Motion that does not explain navigation.

## Motion Must Explain

Motion is part of navigation and trust.

Use motion to show:

- An account row opening into account details.
- A product tile opening into purchase details.
- A payment moving from waiting to success or failure.
- A push approval becoming a consent or transaction result.

Do not use motion as decoration. Do not rely on animation files that slow the app.

## White-Label Without Losing Quality

Bank themes can change:

- Primary color.
- Secondary color.
- Accent color.
- Logo.
- Copy tone where legally required.

Bank themes cannot change:

- Component anatomy.
- Spacing system.
- Type roles.
- Motion timings.
- Data-fetch rules.
- Accessibility rules.
- Consent clarity.

## Performance Is a Design Rule

Neptune. Signal treats system cost as part of UX.

Examples:

- Card list does not fetch balances.
- Card details can fetch card balance.
- Async LyPay does not block forever; it routes to a status page.
- Heavy maps, statements, and documents load only when requested.
- Lists show useful summaries first, not expensive full payloads.

## Arabic-First, Multilingual Always

Arabic is a first-class layout direction, not a translation pass.

Rules:

- RTL must be designed directly.
- Directional icons flip.
- Numbers and identifiers stay readable.
- English and French use the same component structure.
- Mixed-language UI is only acceptable for brands, handles, and technical identifiers.

## The Neptune. Test

Before adding a component or screen, ask:

- Does it clarify customer state?
- Does it reduce a banking task?
- Does it preserve trust?
- Does it work in Arabic?
- Does it work under another bank brand?
- Can KMP, Flutter, native, and web implement it?
- Does it avoid unnecessary backend load?

If the answer is no, redesign it.
